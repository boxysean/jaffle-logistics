WHAT HAPPENED
  • A winter storm hit Paris 14-16 January; a truck jackknifed on an icy on-ramp.
  • One week produced 570 exceptions - nearly a quarter of the year's.
  • The largest account's freight was in the delayed batch, and its review five days later was tense.
WHAT IT COST
  • Paris ran January at 56.60% on time, against a 97% target.
  • The network took nine weeks - weeks 1 to 9 - to settle.
  • Paris closed on 106 partial or cancelled routes; the other hubs ran about 9.9 per 100.
WHAT TO DO BEFORE NEXT WINTER
  1. Move the biggest account's winter freight off Paris. Paris in winter is a dated risk, not a surprise; Berlin and Vienna ran the year better.
  2. Call the customer before the service level breaks. The record shows they raised it first.
  3. Read the storm and the trend apart. Under the recovery sits a weather-independent slide.

WHY CONTEXT ENGINEERING

The case for modelling the business once, before anything reads it
THE REVIEW MOVES UPSTREAM
Nobody reviews an agent's every step.

So the context has to be right before the work runs. The review moves upstream, to the data the agent reads, instead of downstream at the output it produced.

You cannot check every answer, so you have to get the inputs right.

THE CONTEXT GAP
AI rolled out to every employee in a year, and the context those tools read never rolled in.

The tools arrived; the shared understanding of the business did not arrive with them.

TEN WIRES, ONE LAYER
Each of those tools wired itself straight to raw — and one shared context layer replaces the wiring.

Ten tools wired to raw data is ten integrations and ten versions of the truth. Modelled once in a context layer, every tool reads the same thing.

PAID FOR ONCE
Unengineered context gets paid for three times.
Engineered context is paid for once.
  1. Paid once to wire the raw data again for each tool;
  2. paid again to keep that wiring correct as the sources move;
  3. and paid a third time by whoever acts on an answer that was wrong.
An argument, not a measurement. The context layer is built; the agents on top are a design.

WHY THE DATA TEAM

Modeling data for BI was analytics engineering. Modeling it for AI is context engineering.
A DIFFERENT CONSUMER
Analytics engineering modelled data so a person could read it.

The right grain, the joins, a metric's definition written down, tests on what must never be null.

Context engineering models that same data so an agent can read it.

Same craft — for a reader who never asks a clarifying question, and never notices a wrong answer.

LOAD-BEARING FOR AI
Tests, documented definitions and contracts were good practice for BI.

For AI they are load-bearing: on the tables an agent reads by name.

Our own audit found the contracts and exposures still missing — which is why this slide matters.

THE TEAM THAT OWNS THE DATA
The team that owns the data now owns how good the company's AI gets.

Model quality became answer quality. If the definition of "on time" is wrong in the model, every agent that reads it is wrong — and confidently so.

An argument, not a measurement. The context layer is built; the agents are a design.

HOW IT IS RUN
  • Modelled in dbt on the dbt Platform: 24 staging, 3 intermediate, 8 mart and 25 context models (23 AI).
    The AI layer is gated behind ai_functions_enabled — never built as a side effect of an ordinary build.
  • One platform job rebuilds it all from source. Last full rebuild: 42 minutes — seed 5.4, run 35.3, test 0.9.
  • Every model is tested on every build, and a failing test stops the release.
  • Cheap checks first: the whole project builds and tests locally in a minute or two, so a change is proved before it is ever run against the warehouse.

WE AUDITED OURSELVES

What dbt's quality layer found when we pointed it at our own project
WHAT RUNS ON EVERY CHANGE

WHAT WE FIXED
  • The on-time metric had no null guard. Its status test ignored nulls, so a null could skew the rate on a green build. not_null now guards all four inputs.
  • Two tests could never fail, so both were deleted, not counted.
WHAT WE HAVE NOT FIXED
  • No unit tests. The logic most likely to break silently is engine-specific: the shipment-ID regex and the transcript parser each branch per engine, and the local check only exercises the DuckDB branch - so the production branch is never checked against known inputs before it runs.
  • No contracts, access levels or exposures. Two agent skills read knowledge_base and fct_shipments by name. A column rename would break them with no build-time signal.
  • The on-time rule is written out in three places. Three copies drift.
Full audit: reports/dbt-best-practices-audit.md

THE AGENT THAT ANSWERS IT

An agent on the warehouse that already exists:

  1. reads the case and the account behind it
  2. retrieves from knowledge_base by cosine
  3. classifies it with the 23-model AI layer
  4. pulls the contract's SLA and the route's status
  5. drafts the reply; routes the breach to the owner
NOT RUNNING TODAY

This is a design, not a deployment.

The warehouse, the embeddings, the retrieval and the classifiers are real.

The agent is what they make possible.
